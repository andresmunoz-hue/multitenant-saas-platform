1. Contexto
Formas parte del equipo de Data & Analytics dentro de Apex Digital / M5, área transversal que habilita productos analíticos y datos gobernados para múltiples unidades de negocio de una corporación multinacional de bebidas y alimentos (CBC, Beliv, BIA, entre otras).
La organización está consolidando una plataforma de datos empresarial sobre Databricks + ADLS Gen2 + Unity Catalog, con el objetivo de habilitar productos analíticos y, en una segunda fase, agentes de IA conectados a los datos core del negocio.
El proyecto SAAS define una metodología de ingesta y procesamiento aplicable de forma multi-empresa / multi-tenant: cada unidad de negocio (tenant) puede onboarding-arse al pipeline con mínima fricción, manteniendo aislamiento lógico de datos, trazabilidad y consistencia de estándares.
La arquitectura del proyecto ya está definida y se documenta en la sección 5 de este documento. El objetivo de la prueba es implementar el pipeline sobre esa arquitectura, no diseñarla desde cero.

5. Arquitectura provista
Esta sección define la arquitectura de referencia del proyecto SAAS. La implementación debe ceñirse a estas convenciones. Cualquier desacuerdo se registra en docs/observations.md para discusión en la sustentación.
5.1 Visión general
La plataforma sigue el patrón Medallion con tres capas lógicas. Cada capa cumple un rol específico y solo lee de la inmediata anterior:
RAW: archivos crudos tal como llegan de la fuente, sin transformación. Solo lectura.
Bronze: datos ingestados en formato Delta, preservando esquema original más columnas técnicas. Particionado por fecha y tenant.
Silver: datos limpios, normalizados, enriquecidos con dimensiones (SCD Type 2). Es la zona de verdad para consumo analítico downstream.
Gold: agregaciones y métricas de negocio. Modelado dimensional ligero.
5.2 Estrategia de aislamiento multi-tenant
El proyecto SAAS adopta aislamiento por schema dentro de un catálogo único por ambiente. Cada tenant tiene su propio schema en Unity Catalog. Esta decisión optimiza para:
Onboarding ágil de nuevos tenants (no requiere crear catálogos, solo schemas).
Gobierno centralizado de grants y políticas a nivel de catálogo.
Compatibilidad con escenarios de análisis cross-tenant futuros (vistas en gold).
Estructura de naming en Unity Catalog:
  saas_<env>.bronze_<tenant>.<table>
  saas_<env>.silver_<tenant>.<table>
  saas_<env>.gold_<tenant>.<table>
 
  Ejemplos:
    saas_dev.bronze_sv.deliveries
    saas_dev.silver_sv.fact_deliveries
    saas_dev.silver_sv.dim_materials
    saas_dev.gold_sv.daily_metrics_by_delivery_type

Para esta prueba, donde Unity Catalog no aplica, se mapea a la estructura de paths siguiente. Esta es la estructura que el candidato debe implementar:
  data/<layer>/<tenant>/<table>/fecha_proceso=YYYYMMDD/   # por tenant
  data/<layer>_quarantine/<tenant>/<table>/               # cuarentena
  data/shared/quality_logs/                               # cross-tenant
 
  Ejemplos:
    data/bronze/sv/deliveries/fecha_proceso=20250314/
    data/silver/sv/fact_deliveries/fecha_proceso=20250314/
    data/silver_quarantine/sv/fact_deliveries/
    data/shared/quality_logs/

Todas las tablas se escriben como Delta. La estructura de paths refleja la estructura de catálogos en Unity Catalog (sección anterior); en una migración a Databricks, los paths se mapean a tablas Unity con los mismos nombres lógicos.
5.3 Convenciones de naming
Tablas y columnas: snake_case en todas las capas.
Tablas Silver de hechos: prefijo fact_. Dimensiones: prefijo dim_.
Tablas Gold: nombre descriptivo del agregado, sin prefijo (ej: daily_metrics_by_delivery_type).
Columnas técnicas: prefijo guion bajo (_ingestion_timestamp, _source_file, _tenant_id, _batch_id).
Flags booleanos: prefijo is_ (ej: is_routine_delivery, is_bonus_delivery).
Fechas en columnas técnicas: timestamp UTC; en columnas de negocio: tipo date.
Códigos de tenant en minúscula en paths, schemas y la columna _tenant_id. La columna pais del CSV viene en mayúscula (SV, HN, etc.); el código debe normalizarla a minúscula al ingresar a Bronze.
5.4 Particionado
Bronze: particionado por fecha_proceso (yyyymmdd) y tenant_id.
Silver fact_deliveries: particionado por fecha_proceso. La separación por tenant ya viene dada por el schema.
Silver dim_materials: no particionado (cardinalidad baja).
Gold: particionado por fecha si la tabla lo amerita por cardinalidad.
5.5 Idempotencia y reprocesos
La estrategia definida para garantizar idempotencia entre capas:
Bronze: overwrite por partición (replaceWhere o equivalente sobre fecha_proceso + tenant_id). Una reejecución del mismo rango sobrescribe la partición correspondiente, no duplica.
Silver fact_deliveries: MERGE INTO con clave de negocio compuesta (tenant_id, fecha_proceso, transporte, ruta, material, tipo_entrega). Actualiza si existe, inserta si no.
Silver dim_materials: MERGE INTO con lógica SCD Type 2 sobre la clave material + valid_from.
Gold: recomputo completo por partición de fecha. Las tablas Gold son derivadas, no autoritativas.
5.6 Manejo de anomalías
La política definida para cada tipo de anomalía:
Tipo de anomalía
Acción
Justificación
fecha_proceso nula o inválida
Cuarentena
Sin fecha no puede asignarse a partición. Revisión manual posterior.
cantidad nula, negativa o cero
Cuarentena
Posible error de origen. No descartar silenciosamente.
material no presente en el catálogo
Cuarentena
Romper integridad referencial debe ser visible y auditable.
tipo_entrega fuera de las 4 válidas
Descarte
Regla de negocio: COBR y Z99 no pertenecen al alcance analítico.
duplicado exacto (todas las columnas)
Deduplicar
Conservar una sola copia. No tratar como anomalía visible.
precio nulo
Cuarentena
Sin precio las métricas de ingreso no son calculables.

Las filas en cuarentena se escriben en una tabla paralela <layer>_quarantine_<tenant>.<table> con la columna técnica _quarantine_reason. Los descartes se contabilizan en métricas pero no se persisten.
5.7 SCD Type 2 sobre dim_materials
El catálogo de materiales se modela como SCD Type 2 con las siguientes reglas:
Clave de negocio: material (SKU).
Atributos versionados: descripcion, categoria, precio_base.
Columnas de control: valid_from, valid_to, is_current.
Una sola fila puede tener is_current = true por cada SKU.
Las transacciones Silver se enriquecen con la versión vigente del material a la fecha del proceso, no con la versión actual. Esto requiere un join temporal de la forma:
  fact_deliveries.fecha_proceso BETWEEN dim_materials.valid_from
                                  AND dim_materials.valid_to

5.8 Configuración
Estructura jerárquica con OmegaConf:
  config/base.yaml            # defaults compartidos
  config/env/<env>.yaml       # overrides por ambiente (dev/qa/main)
  config/tenants/<tenant>.yaml # overrides por tenant

Parámetros mínimos a soportar:
paths.bronze, paths.silver, paths.gold (rutas base por capa; el código compone el resto: <base>/<tenant>/<table>/...)
paths.quarantine_root (ruta base; el código compone <quarantine_root>/<layer>_quarantine/<tenant>/<table>/)
paths.quality_logs (ruta a la tabla Delta compartida de logs de calidad)
execution.start_date, execution.end_date (rango de fecha_proceso a procesar, formato YYYY-MM-DD)
execution.tenant (un código de tenant en minúscula, o "all" para procesar todos)
execution.fail_fast (bool, default false): comportamiento cuando --tenant all y uno falla. Si true, aborta toda la corrida; si false, continúa con los demás tenants y reporta el fallo al final.
quality.fail_on_critical (bool, default false): si una validación crítica falla, abortar antes de Gold para ese tenant.
5.9 Tabla de logs de calidad
Toda validación ejecutada se registra como tabla Delta en la ruta data/shared/quality_logs/ (en Databricks productivo: <env>.shared.quality_logs), con el siguiente esquema:
  _run_id            string
  _batch_id          string
  tenant_id          string
  layer              string  # bronze | silver | gold
  table_name         string
  check_name         string
  check_severity     string  # critical | warning | info
  records_checked    long
  records_failed     long
  check_passed       boolean
  executed_at        timestamp

6. Implementación requerida
Implementa el pipeline siguiendo la arquitectura definida en la sección 5. Las siguientes son las características obligatorias:
6.1 Configuración (obligatorio)
Parámetros controlados vía YAML con OmegaConf, en la estructura jerárquica definida en 5.8.
Ejecución por tenant específico (--tenant sv) o todos (--tenant all).
Rango de fechas parametrizable (--start-date, --end-date) con valor de fecha_proceso.
Configuración mínima por ambiente: dev / qa / main (al menos los paths deben cambiar).
6.2 Capa Bronze
Ingesta del CSV a formato Delta, preservando esquema original.
Particionado por fecha_proceso y tenant_id (según 5.4).
Idempotencia por overwrite de partición (según 5.5).
Columnas técnicas requeridas: _ingestion_timestamp, _source_file, _tenant_id, _batch_id.
6.3 Capa Silver
fact_deliveries con MERGE INTO según clave de negocio definida en 5.5.
Normalización de unidades: convertir CS a ST (1 CS = 20 ST). Todos los registros deben quedar en unidad común.
Filtrado de tipo_entrega: solo ZPRE, ZVE1, Z04, Z05.
Flags is_routine_delivery (ZPRE, ZVE1) e is_bonus_delivery (Z04, Z05).
Aplicación de las reglas de manejo de anomalías definidas en 5.6 (cuarentena en tabla paralela, descartes contabilizados).
dim_materials implementada como SCD Type 2 según 5.7.
Enriquecimiento de fact_deliveries con dim_materials usando join temporal (no usar solo is_current).
6.4 Capa Gold
Construye al menos una tabla Gold: daily_metrics_by_delivery_type por tenant. Granularidad: una fila por (tenant_id, fecha_proceso, tipo_entrega), con las métricas:
total_units: suma de cantidad ya normalizada a ST (columna calculada en Silver, no la cantidad original).
total_revenue: suma de (cantidad_normalizada_st * precio_transaccion). Usar el campo precio de la transacción, no precio_base del catálogo. El precio del catálogo se preserva en Silver como columna informativa, pero el revenue real es el de la transacción.
active_routes: count distinct de ruta.
active_transports: count distinct de transporte.
6.5 Calidad de datos
Implementa al menos 3 validaciones sobre Silver. Pueden ser checks propios bien estructurados.
Los resultados se persisten en la tabla quality_logs según el esquema de 5.9.
Cada validación declara su severidad (critical / warning / info).
Si quality.fail_on_critical = true en config y alguna validación crítica falla, el pipeline debe abortar antes de Gold.

Anexo A — Código para revisar
Coloca el siguiente código en /mentoring/bad_code.py. No lo modifiques ahí; el refactor va en good_code.py.
import pandas as pd
from pyspark.sql import SparkSession
 
spark = SparkSession.builder.getOrCreate()
 
def process(file_path, country):
    df = pd.read_csv(file_path)
    df = df[df["pais"] == country]
    result = []
    for i, row in df.iterrows():
        if row["tipo_entrega"] == "ZPRE" or row["tipo_entrega"] == "ZVE1":
            if row["unidad"] == "CS":
                qty = row["cantidad"] * 20
            else:
                qty = row["cantidad"]
            result.append({
                "pais": row["pais"],
                "fecha": row["fecha_proceso"],
                "material": row["material"],
                "cantidad_st": qty,
                "total": qty * row["precio"]
            })
    out = pd.DataFrame(result)
    sdf = spark.createDataFrame(out)
    sdf.write.mode("overwrite").parquet("/tmp/output/" + country)
    print("done")
    return out
 
process("data.csv", "GT")

Áreas de mejora a considerar: uso de pandas donde corresponde Spark nativo, iteración fila por fila, lógica de negocio hardcoded, ausencia de validaciones y tipado, naming inconsistente, manejo de errores inexistente, escritura no idempotente, ausencia de tests, falta de soporte multi-tenant.
